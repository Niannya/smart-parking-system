## 1. 项目背景

传统停车场依赖人工登记车辆进出、判断空闲车位和计算停车费用，容易出现信息更新不及时、费用计算不一致、历史记录难以查询等问题。

本项目拟开发一套前后端分离的智能停车场管理系统，实现停车位、车辆进出、停车计费、收费记录和经营数据的统一管理。系统中的“智能”主要体现在自动分配车位、自动计算停车时长与费用、实时更新车位状态和自动汇总经营数据，不以人工智能或真实硬件识别为必选内容。

## 2. 项目目标

1. 准确记录车辆入场、停车和离场的完整过程。
2. 统一管理多个停车场及其区域、停车位和实时状态。
3. 根据各停车场自己的收费规则自动计算停车费用。
4. 保存停车记录和收费记录，支持条件查询。
5. 统计车位使用情况、车辆流量和停车收入。
6. 通过数据库约束和事务保证核心数据的一致性。
7. 支持车主登录、绑定本人车辆并查看自己的停车记录和费用。

## 3. 项目范围

### 3.1 本课程设计必须实现

- 管理员和车主登录，并按角色限制可访问的功能。
- 车主绑定本人车牌并查看自己的停车记录。
- 多个停车场的新增、修改、启用和停用。
- 停车区域和停车位管理。
- 车辆入场登记。
- 空闲车位查询与自动分配。
- 车辆离场登记。
- 停车时长和费用自动计算。
- 收费确认与收费记录保存。
- 在场车辆和历史停车记录查询。
- 车位数量、车位占用率、车辆流量和收入统计。

## 4. 系统参与者

| 参与者 | 主要职责 |
| --- | --- |
| 管理员 | 登录系统；管理全部停车场及其区域、停车位和收费规则；办理车辆入场、离场及收费；查看全部或指定停车场的记录与统计数据 |
| 车主 | 登录系统；绑定或停用自己的车辆；查看本人车辆的当前停车状态、历史停车记录和费用信息 |

本课程设计设置管理员和车主两类角色。管理员之间不再细分操作员等岗位，所有管理员都能管理系统内全部停车场；车主只能访问与本人账号和本人车辆有关的功能，不能进入管理页面或查看其他车主的数据。

## 5. 业务术语

| 术语 | 含义 |
| --- | --- |
| 停车场 | 系统管理的具体停车地点，具有唯一编号、名称、地址和状态 |
| 停车区域 | 某个停车场内的分区，例如 A 区、B 区 |
| 停车位 | 可供车辆停放的具体位置，具有唯一编号和当前状态 |
| 车主 | 在系统中注册并绑定本人车辆的普通用户，只能查看自己的停车信息 |
| 车辆 | 由车主绑定的普通小型汽车，以唯一车牌号码识别；未绑定车辆也可作为临时车辆入场 |
| 在场车辆 | 已完成入场登记但尚未完成离场的车辆 |
| 停车记录 | 一辆车从入场到离场的一次完整停车过程 |
| 收费规则 | 系统计算停车费用时使用的计价规则 |
| 收费记录 | 对一次停车费用的支付结果记录 |

## 6. 核心业务流程

### 6.1 车辆入场流程

1. 管理员选择车辆即将进入的停车场，并输入车牌号码。本课程设计只支持普通小型汽车，不再选择车辆类型。
2. 系统校验车牌号码格式，并检查该车辆是否已经在场。
3. 系统只在所选停车场内查询符合条件的空闲停车位。
4. 系统在所选停车场内自动分配一个空闲车位；管理员也可在允许的情况下手动选择该停车场内的车位。
5. 如果车牌已被有效车主账号绑定，系统自动关联该车辆；未绑定车牌仍可作为临时车辆入场。
6. 系统创建停车记录，保存所属停车场、车牌快照、车辆关联、入场时间和停车位。
7. 系统将该停车位状态改为“占用”。
8. 页面显示入场成功、停车位编号和入场时间。

异常情况：

- 车牌号码格式错误时，不允许登记。
- 同一车牌已经在场时，不允许重复入场。
- 没有符合条件的空闲车位时，提示“停车场已满”并停止登记。
- 入场记录创建失败时，不得单独改变停车位状态。

### 6.2 车辆离场与收费流程

1. 管理员输入车牌号码或停车记录编号。
2. 系统查找该车辆当前未结束的停车记录。
3. 系统根据入场时间、离场时间和该记录入场时绑定的停车场收费规则计算停车时长与应收金额。
4. 管理员确认支付方式和实收金额。
5. 系统创建收费记录，并将停车记录标记为已完成。
6. 系统将对应停车位状态改为“空闲”。
7. 页面显示停车时长、应收金额、实收金额和离场时间。

异常情况：

- 找不到在场记录时，不允许直接办理正常离场。
- 支付未确认时，不完成正常离场。
- 离场处理失败时，停车记录、收费记录和车位状态必须保持原状。
- 特殊情况下允许管理员将记录标记为“异常”，并填写处理备注。

### 6.3 停车场与停车位维护流程

1. 管理员新增、修改、启用或停用停车场。
2. 管理员在指定停车场内新增或修改停车区域。
3. 管理员在区域内新增停车位。本课程设计不区分普通、充电等停车位类型。
4. 管理员可将空闲停车位设为“停用”，用于维修或其他情况。
5. 已被车辆占用的停车位不能直接删除或停用。
6. 已产生停车记录的停车场、区域和停车位原则上不物理删除，可改为停用。

### 6.4 查询与统计流程

1. 管理员进入管理首页，选择查看全部停车场或某个停车场的实时概况。
2. 系统按所选范围展示总车位数、空闲数、占用数、停用数和占用率。
3. 管理员可按停车场、车牌号码、停车位、时间范围和停车状态查询记录。
4. 管理员可按停车场、日期或指定时间范围查看入场数量、离场数量和收入。

### 6.5 车主使用流程

1. 车主可以注册普通账号；注册接口只能创建车主角色，不能创建管理员。
2. 车主使用账号和密码登录系统。
3. 车主绑定本人车辆的车牌号码；同一车牌不能同时绑定给多个车主。
4. 车辆入场时，如果车牌已绑定，系统自动把停车记录关联到该车辆。
5. 车主可以查看本人车辆所在停车场、当前停车状态、历史停车记录、停车时长和费用。
6. 车主不能办理入场、离场和收费，也不能访问停车区域、车位、收费规则及统计管理功能。

## 8. 业务规则

### 8.1 停车场状态规则

停车场使用以下两种状态：

| 状态 | 含义 | 允许的主要操作 |
| --- | --- | --- |
| 启用 | 可以维护区域、配置规则并办理车辆入场 | 查询、修改、停用、办理业务 |
| 停用 | 暂停办理新的车辆入场 | 查询、修改、重新启用 |

- 启用 → 停用：管理员停用当前没有在场车辆的停车场。
- 停用 → 启用：管理员重新启用停车场。
- 停用停车场保留历史区域、车位、收费规则、停车记录和收费记录。
- 停用停车场不能办理新的车辆入场。

### 8.2 停车位状态规则

停车位使用以下三种状态：

| 状态 | 含义 | 允许的主要操作 |
| --- | --- | --- |
| 空闲 | 可以分配给入场车辆 | 分配、修改、停用 |
| 占用 | 当前已有车辆使用 | 办理对应车辆离场 |
| 停用 | 暂时不能使用 | 重新启用 |

状态变化必须符合以下规则：

- 空闲 → 占用：车辆成功入场。
- 占用 → 空闲：车辆成功完成离场。
- 空闲 → 停用：管理员停用车位。
- 停用 → 空闲：管理员重新启用车位。
- 占用状态不能直接改为停用。

### 8.3 停车记录状态规则

| 状态 | 含义 |
| --- | --- |
| 停车中 | 已入场但未离场 |
| 已完成 | 已完成收费与离场 |
| 异常 | 因数据错误或特殊情况转入人工处理 |

- 同一车牌同一时间最多只能有一条“停车中”记录。
- 一条正常停车记录必须关联一个停车位。
- 已绑定车辆入场时应关联车辆实体；临时车辆的车辆关联允许为空，但车牌快照必须保存。
- “已完成”记录必须具有离场时间，且离场时间不能早于入场时间。
- 已完成记录中的费用数据不得因以后修改收费规则而变化。

### 8.4 收费规则

为了控制课程设计的工作量，采用“免费时长 + 按小时计费 + 不足一小时按一小时计算 + 每 24 小时封顶”的方式。

每个停车场独立维护收费规则。演示数据中各停车场可以先使用相同的默认规则：

- 免费时长：30 分钟。
- 总停车时间不超过 30 分钟时，费用为 0 元。
- 超过 30 分钟后，只对超出免费时长的部分计费。
- 计费单位：1 小时。
- 单位价格：5 元/小时。
- 不足 1 小时的部分按 1 小时计算。
- 每个连续 24 小时计费周期的费用最高为 50 元。
- 跨越 24 小时时，将计费时长按连续 24 小时拆分；每个完整周期最多收取 50 元，剩余不足 24 小时的部分继续按小时计算且最高收取 50 元。
- 30 分钟免费时长在一次停车过程中只享受一次，不会在每个 24 小时周期重新计算。
- 同一停车场内的所有普通小型汽车使用该停车场当前规则，不按车型或停车位类型区分价格；不同停车场可以配置不同规则。

计算示例：总停车时间为 26 小时时，扣除一次 30 分钟免费时长后，计费时长为 25.5 小时。前 24 小时按封顶金额 50 元计算，剩余 1.5 小时按 2 小时计算为 10 元，总费用为 60 元。

### 8.5 金额规则

- 金额统一保留两位小数。
- 应收金额不能为负数。
- 实收金额不能为负数。
- 本课程设计的支付方式可使用“现金”“电子支付”“免费放行”三个模拟选项，不接入真实支付平台。
- 免费放行应要求填写原因，并由管理员操作。

## 9. 数据需求

本课程设计需要管理以下核心数据对象：

| 数据对象 | 主要内容 |
| --- | --- |
| 用户账号 | 管理员和车主的登录账号、密码摘要、姓名、角色、账号状态 |
| 车辆 | 车牌号码、所属车主、绑定状态；同一车牌只能绑定一个车主 |
| 停车场 | 停车场编号、名称、地址、说明、状态 |
| 停车区域 | 所属停车场、区域编号、区域名称、说明、状态 |
| 停车位 | 停车位编号、所属区域、当前状态 |
| 停车记录 | 所属停车场、车牌快照、可选车辆关联、停车位、入场时间、离场时间、停车状态、计费结果 |
| 收费规则 | 所属停车场、免费时长、计费单位、单位价格、封顶金额、生效时间 |
| 收费记录 | 对应停车记录、应收金额、实收金额、支付方式、支付时间、办理管理员 |

数据之间至少应满足以下关系：

- 一个停车场包含多个停车区域，也可以有多条历史收费规则。
- 一个停车区域只属于一个停车场，并包含多个停车位。
- 一个车主账号可以绑定多辆车，一辆车只能属于一个车主。
- 一辆已绑定车辆可以产生多条历史停车记录。
- 一个停车位可以产生多条历史停车记录，但同一时刻最多有一条进行中的记录。
- 一个车牌可以产生多条历史停车记录，但同一时刻最多有一条进行中的记录。
- 一条正常完成的停车记录对应一条收费记录。
- 一条收费规则可以被多条停车记录使用。

> 本节只描述业务数据，不在需求阶段确定表名、字段名、主键类型和 SQL。相关内容应在 ER 图和数据库设计阶段完成。

## 11. 非功能需求

### 11.1 数据正确性

- 车辆入场时，创建停车记录与占用停车位必须作为一个完整操作成功或失败。
- 车辆离场时，更新停车记录、保存收费记录与释放停车位必须作为一个完整操作成功或失败。
- 数据库应通过主键、唯一约束、外键、非空约束和检查约束保证基本数据合法性。
- 涉及多个数据更新的核心业务应使用事务。

### 11.2 性能

- 在课程演示数据规模下，普通列表和详情查询应在 2 秒内返回。
- 常用查询条件应在数据库设计阶段考虑索引，例如车牌号码、停车状态、入场时间和支付时间。

### 11.3 安全性

- 用户密码不能以明文保存，应保存安全的密码摘要。
- 后端必须校验用户角色和数据归属，不能只通过隐藏前端菜单实现权限控制。
- 车主查询停车记录时，后端必须根据当前登录账号限制为本人车辆，不能接受任意车主编号绕过权限。
- 数据库密码等本机配置不得提交到 Git 仓库。
- 后端应校验用户输入，不能只依赖前端校验。
- 错误响应不得返回数据库密码、SQL 堆栈等敏感信息。

### 11.4 可维护性

- 前端、后端和数据库脚本分目录管理。
- 接口返回格式、命名规则和错误处理方式保持统一。
- 数据库初始化和演示数据应通过脚本提供，便于组员搭建相同环境。
- 重要业务规则应有测试或可重复的验收步骤。

### 11.5 兼容性

- 后端使用项目规定的 JDK 21 和 Maven Wrapper。
- 数据库使用 PostgreSQL。
- 前端在当前主流 Chromium 浏览器中正常运行。

## 12. 验收标准

### 12.1 核心流程验收

1. 系统存在空闲停车位时，输入一个未在场的合法车牌，能够成功入场并获得车位。
2. 车辆只能分配到管理员所选停车场中的空闲车位。
3. 入场完成后，对应车位立即变为占用，在场车辆列表出现该车辆。
4. 同一车牌再次办理入场时，系统拒绝操作且不产生重复记录。
5. 所选停车场的所有可用车位被占用或停用时，新车辆不能入场。
6. 对在场车辆办理离场时，系统按照入场停车场绑定的规则正确计算停车时长和费用。
7. 确认支付后，停车记录变为已完成，收费记录被保存，车位恢复为空闲。
8. 任一离场步骤失败时，不产生“车位已释放但停车记录未完成”等不一致数据。

### 12.2 查询与统计验收

1. 能按车牌号码查到该车辆的当前记录和历史记录。
2. 能按时间范围查询停车记录和收费记录。
3. 首页车位总数等于空闲、占用和停用数量之和。
4. 车位占用率计算结果与实际占用数量一致。
5. 指定日期的收入统计等于该日期有效收费记录实收金额之和。
6. 按指定停车场查询和统计时，不混入其他停车场的数据。
7. 车主登录后只能看到本人已绑定车辆所关联的停车记录。
8. 车主直接请求管理接口或其他车主的数据时，系统拒绝访问。

### 12.3 车主功能验收

1. 普通用户能够注册车主账号并登录，且不能通过注册参数获得管理员角色。
2. 车主能够绑定一个尚未被其他账号绑定的合法车牌。
3. 同一车牌不能重复绑定给其他车主。
4. 已绑定车辆入场后，车主能够查看本次停车状态和费用信息。
5. 未绑定车辆仍能由管理员正常办理入场、离场和收费。
6. 车主不能办理车辆入场、离场、收费或修改停车场基础数据。

### 12.4 工程验收

1. 新组员按仓库文档配置环境后可以启动前端、后端和数据库。
2. 仓库中不包含任何组员的真实数据库密码。
3. 数据库初始化脚本可以在空数据库中重复执行并建立所需结构。
4. 核心接口有统一的成功和失败响应。
5. 项目演示前，`dev` 分支上的前后端能够完成一条完整的入场到离场流程。

## 13. 需求讨论结论

以下结论作为本课程设计的需求范围和后续设计依据：

| 编号 | 讨论问题 | 小组结论 |
| --- | --- | --- |
| Q-01 | 管理端是否区分管理员与操作员？ | 不区分；所有管理员拥有相同管理权限 |
| Q-02 | 系统管理一个还是多个停车场？ | 管理多个停车场；停车区域、收费规则、停车记录和统计均按停车场归属 |
| Q-03 | 本课程设计支持哪些车辆类型？ | 只支持普通小型汽车，按车牌号码管理，不区分车型 |
| Q-04 | 是否区分普通车位、充电车位等车位类型？ | 不区分 |
| Q-05 | 自动分配车位采用什么规则？ | 只在所选停车场内，将空闲车位按区域编号、车位编号升序排列，分配第一个可用车位 |
| Q-06 | 免费时长、单位价格、计费单位和每 24 小时封顶金额分别是多少？ | 30 分钟免费；超出部分每小时 5 元；不足 1 小时按 1 小时；每连续 24 小时封顶 50 元 |
| Q-07 | 跨天停车的封顶费用如何计算？ | 按连续 24 小时周期累计；完整周期最高 50 元，剩余时长按小时计算且最高 50 元；免费时长整次停车只享受一次 |
| Q-08 | 收费规则按入场时还是离场时的有效规则执行？ | 入场时绑定所属停车场当时有效的收费规则 |
| Q-09 | 是否允许未支付先离场？ | 不允许；异常放行必须由管理员处理并填写原因 |
| Q-10 | 本课程设计是否实现登录和角色权限？ | 实现管理员与车主登录；管理员拥有管理权限，车主只能管理本人车辆并查看本人记录 |
| Q-11 | 是否需要导出 Excel 或打印收费凭证？ | 不作为必做功能；核心功能完成后可选做 Excel 导出，不实现打印凭证 |
| Q-12 | 课程最终验收或教师是否还有指定功能？ | 否 |
| Q-13 | 是否建立车主和车辆数据？ | 建立统一用户账号和车辆数据；车主可绑定车辆并查看本人记录，临时车辆仍可入场 |
| Q-14 | 管理员是否按停车场分别授权？ | 不分别授权；所有管理员均可管理全部停车场 |

## 14. 需求变更规则

1. 本文经全组确认后，作为本课程设计的需求基线和最终验收依据。
2. 新增需求前应判断是否影响数据库结构、接口和现有页面。
3. 会影响核心表结构或核心流程的需求，需要全组确认后再修改。
4. 新想法优先记录为“可选加分项”，不要在必做功能未完成时直接开发。
5. 每次需求变更应同步更新本文，并在提交说明中写明变更内容。

7. 完成测试、演示数据和项目说明文档。
