# 智能停车场管理系统：工程实施总契约

> 状态：实施约定草案；2026-11-16。三人确认后作为开发契约。本文描述**最终要实现什么**，不表示当前代码已实现。
> 项目为三人课程设计，交付一套支持多个停车场的完整系统，不按商业产品分“第一版／后续版”。

## 1. 给组员和 AI 的阅读顺序

1. 先读本文件；再读[接口契约](01_接口与数据契约.md)和自己在[成员任务书](02_三人成员任务书.md)中的章节。
2. 实现业务规则时对照[需求分析](../智能停车场管理系统_需求分析.md)第 7、8、12 节、[数据字典](../database-design/数据字典.md)及[建表脚本](../../database/01_schema.sql)。这些是已有业务和数据库事实；本文件只补齐原文未明确的工程决策。
3. 每次从最新 `dev` 创建本任务分支，只修改[文件归属表](#5-文件归属与冲突边界)允许的文件。缺少公共方法时先在 PR 描述写明契约需求，不复制一套公共类。
4. 交付代码、测试、PR 说明和[验收记录](../milestones/停车场项目_里程碑验收记录.md)中的对应证据。编译通过不等于业务验收通过。

## 2. 已确认仓库现状与最终目标

仓库当前集成基线为 `dev`。数据库结构与演示数据已由 [PR #5](https://github.com/Niannya/smart-parking-system/pull/5) 合入；[PR #6](https://github.com/Niannya/smart-parking-system/pull/6) 停车区域处于审查中。现有 `AdminController`、`/api/instructors`、教师展示页和 `/api/database` 是框架演示残留，不是停车系统已完成模块，成员 1 在公共基础 PR 中删除或限制它们，不让它们成为无鉴权的正式接口。

最终可演示两种身份：

- `ADMIN`：管理账号状态及所有停车场、区域、车位、收费规则；办理入场、离场；查看全部记录和统计。
- `OWNER`：注册/登录，绑定或停用本人车辆，只查看本人已绑定车辆关联的停车记录和费用；不能办理管理员业务。

至少两个停车场同时存在，任何区域、车位、收费规则、停车记录及统计均有明确停车场归属；不能因前端选错或修改请求参数而串场。

## 3. 技术与工程决策（所有任务统一）

| 项 | 固定做法 | 验证 |
| --- | --- | --- |
| 后端 | 现有 Spring Boot 3.2.5、Java 21、Maven Wrapper、MyBatis XML；不引入第二套 ORM | `backend\mvnw.cmd test`、`package` |
| 数据库 | PostgreSQL；沿用已合并的 8 张表与约束。新增结构必须由成员 1 提单独 SQL/数据字典 PR，经成员 2、3 确认 | 空库初始化和关键 SQL 查询 |
| 前端 | 现有 Vue 3、Vite、Axios、Element Plus；成员 1 统一加入 Vue Router 和开发代理 | `npm ci`、`npm run build` |
| 身份 | 成员 1 加入与 Boot 3.2.5 管理版本相配的 Spring Security；使用服务器会话、`HttpOnly` 会话 Cookie；不把身份写在请求体、不把凭据存 `localStorage` | 401/403、刷新保留身份、退出失效 |
| CSRF | 会话登录的写请求使用 CSRF token；前端先取得 token，写请求放 `X-XSRF-TOKEN`；登录/退出后刷新 token。配置需与实际 Spring Security 6.2.x 版本匹配 | 无 token 写请求被拒，有 token 正常 |
| 前后端开发连接 | Vite 将 `/api` 原样代理到 `http://localhost:8081`；前端只调用相对路径 `/api/...`，不在各页面写死后端完整 URL | 浏览器同源请求可带会话 |
| API | JSON `camelCase`；成功/失败均使用第 4 节响应包；请求字段由后端再次校验 | 请求/响应契约测试 |
| 金额与时间 | Java `BigDecimal`、数据库 `NUMERIC(10,2)`；时间由服务器生成，API 输出含时区的 ISO 8601；按 `Asia/Shanghai` 的日期范围统计 | 金额与跨日测试 |
| 数据访问 | 每个模块独立 Controller/Service/Mapper/XML/DTO；事务放 Service；不得由 Controller 直接拼 SQL | 异常回滚测试 |

时间字段在 Java 中统一使用 `OffsetDateTime`，计费函数与业务 Service 注入 `Clock` 以便固定时刻测试；数据库的 `TIMESTAMPTZ` 不靠字符串比较。请求 DTO 用 Bean Validation 或等价显式校验，并在 Controller 边界拒绝未知 JSON 字段，避免三个模块采用不同容错规则。

Spring Boot 3.2.5 管理的 Spring Security 版本见[官方依赖清单](https://docs.spring.io/spring-boot/docs/3.2.5/reference/html/dependency-versions.html)。会话中手动登录须显式保存 `SecurityContext`，见[官方会话文档](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)；SPA 的 CSRF 有 token 刷新和请求处理细节，见[官方 CSRF 文档](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。开发代理用法见[Vite 官方文档](https://vite.dev/config/server-options#server-proxy)。**不要直接复制新版本文档中的 API 写法到 6.2.x；先以项目编译和集成测试核对。**

## 4. 全局外部契约

所有后端业务接口的返回外壳固定为：

```json
{"code":0,"message":"操作成功","data":{}}
{"code":4002,"message":"同一停车场内区域编号已存在","data":null}
```

- `code=0` 表示成功；非 0 是稳定的业务错误码。列表的 `data` 是数组，单对象接口是对象，删除/退出登录成功的 `data` 为 `null`。空列表为 `[]`，不返回 `null`。
- HTTP：成功 200；参数错误 400；未登录 401；角色/归属不符 403；资源不存在 404；状态/唯一冲突 409；未知错误 500。未知错误正文只显示通用提示，具体异常留在服务端日志。认证过滤器产生的 401/403 也必须使用同一 JSON 外壳。
- 字段与完整端点以[接口契约](01_接口与数据契约.md)为唯一来源。客户端不可提交 `createdBy`、`entryAdminId`、`exitAdminId`、`handledBy`、`ownerUserId`、`feeRuleId`、`entryTime`、`exitTime` 等由服务器确定的字段。
- 创建操作返回新对象；修改/启停操作返回修改后对象；不得只返回“成功”导致页面无法更新。
- 业务错误码分段：认证 1001–1099，停车场 2001–2099，区域 4001–4099（保留 PR #6 已用编号），车位 4101–4199，车主车辆 4201–4299，入场 4301–4399，收费规则 4401–4499，离场/支付 4501–4599，记录查询 4601–4699，统计 4701–4799。同一分段内由负责者登记到接口契约，不能重复占号。

## 6. 跨模块内部契约与并发顺序

**共同数据事实**：`parking_record.parking_lot_id`、`parking_space_id` 与 `fee_rule_id` 必须归属同一个停车场；入场时将当时有效规则 ID 固定到记录。成员 3 离场时读取该记录绑定的规则，不能取停车场后来启用的新规则。已绑定的 `ACTIVE` 车辆写 `vehicle_id`；未绑定或已停用的车辆作为临时车，`vehicle_id=null`；无论哪种都保留车牌快照。

为避免停用停车场/区域/车位、切换收费规则与车辆入场互相穿插，成员 1 先交付 `ParkingLotGuard`：

- `lockLot(lotId)`：在当前事务内对停车场行 `SELECT ... FOR UPDATE`，不存在则抛业务异常。
- `lockActiveLot(lotId)`：调用前者并校验 `ACTIVE`。
- 同一个停车场内会改变“能否入场”的操作按固定顺序先锁停车场行，再读/锁区域、车位、规则或在场记录。成员 1 的停车场启停、成员 2 的区域/车位启停与入场、成员 3 的规则切换均遵守这一顺序。离场单独锁在场记录与对应车位，条件更新保证 `OCCUPIED → FREE`。
- 入场在一个事务中：锁启用停车场 → 读当前规则 → 选启用区域的空闲车位并锁/条件占用 → 插入停车记录。SQL 唯一索引 `uk_parking_record_active_plate`、`uk_parking_record_active_space` 是并发兜底；冲突须回滚并给可读 409，不可留下被占用的空车位。
- 停用停车场/区域/车位同样先取得停车场锁，再检查 `PARKING` 记录并更新，不能仅“先查数量、后无条件更新”。删除关联数据前也在事务内校验外键；有历史记录的车位、车辆不物理删除。
- 成员 2 负责入场的事务/车位占用；成员 3 负责离场的事务/车位释放。双方不得相互调用 HTTP 接口；同进程用只读 Service 或 Mapper 契约交接。

这套行锁顺序是本项目的工程决策。若实际 SQL、数据库锁或并发测试显示需调整，必须由成员 1、2、3 共同更新本节和测试，不能各自改一半。

## 8. 必做边界与交付门槛

必做：多停车场隔离、管理员/车主后端鉴权、车辆绑定、区域与车位管理、规则绑定、自动分配、入场/离场事务、计费、支付记录、记录查询、统计和两机复现。可延后：手动指定车位、图表趋势、分页、Excel 导出和界面润色；延后前同步需求分析，不在实现中悄悄省掉必做内容。

每个 PR 必须附：任务 ID；改动文件；依赖的 `dev` 提交/PR；数据库变化；自动化测试命令、字面结果和退出码；至少一个正常、一个拒绝、一个边界用例；前端截图（如有页面）；未完成项。作者之外至少一人审查，合并后重跑最小烟测。最终只在整条业务链通过后提 `dev → main`。
