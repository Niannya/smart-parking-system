## 4. 组员第一次获取项目

### 4.1 安装要求

每位组员至少准备：

- Git。
- JDK 21。
- IntelliJ IDEA。
- Node.js 和 npm。
- PostgreSQL。
- 能访问本仓库的 GitHub 账号。

### 4.2 克隆并切换到开发分支

```bash
git clone https://github.com/Niannya/smart-parking-system.git
cd smart-parking-system
git switch dev
git status
```

正常结果应包含：

```text
On branch dev
Your branch is up to date with 'origin/dev'.
```

在 `main` 尚未合入项目框架之前，不要因为克隆后目录看似为空而重新创建项目，先执行 `git switch dev`。

### 4.3 已经克隆过仓库的组员更新地址

仓库转移后，已有本地仓库不需要重新克隆。在仓库根目录执行：

```bash
git remote set-url origin https://github.com/Niannya/smart-parking-system.git
git remote -v
```

确认 `fetch` 和 `push` 两行都显示 `Niannya/smart-parking-system.git`。旧地址可能暂时自动跳转，但不应继续作为本地远程地址使用。

### 4.4 配置并启动后端

1. 使用 IDEA 打开仓库中的 `backend` 目录。
2. 将 Project SDK 和 Maven Runner JDK 设置为 JDK 21。
3. 打开 `BackendApplication` 的运行配置。
4. 在“修改选项”中显示“环境变量”。
5. 添加 `DB_PASSWORD=自己的数据库密码`。
6. 不勾选“存储为项目文件”。
7. 启动 `BackendApplication`。

当前共享配置为：

```properties
server.port=8081
spring.datasource.url=jdbc:postgresql://localhost:15432/university
spring.datasource.username=Niannya
spring.datasource.password=${DB_PASSWORD}
```

其中数据库地址和用户名仍是最初开发机的测试配置。正式开发前应在独立功能分支中将它们改为环境变量，并切换到 `smart_parking`。

后端基础检查地址：

```text
http://localhost:8081/hello
```

### 4.5 安装并启动前端

在 `frontend` 目录执行：

```bash
npm install
npm run dev
```

浏览器访问：

```text
http://localhost:5173
```

`node_modules` 由每位组员在本机安装，不上传到 GitHub。

## 5. 日常 Git 协作流程

### 5.1 最重要的规则

1. 不直接在 `main` 上开发。
2. 不直接在 `dev` 上编写或提交业务功能。
3. 每次从最新 `dev` 创建新的功能分支。
4. 一个分支只解决一个明确任务。
5. 提交说明使用中文。
6. 功能通过 PR 合并到 `dev`，稳定里程碑再由 `dev` 合并到 `main`。

### 5.2 开始一项新任务

```bash
git switch dev
git pull origin dev
git switch -c feature/任务名称
```

示例：

```bash
git switch -c feature/database-design
git switch -c feature/parking-space-api
git switch -c feature/vehicle-page
```

分支名称使用小写英文和连字符，不使用空格或中文。

### 5.3 开发过程中检查修改

```bash
git status
git diff
```

只添加本次任务相关文件：

```bash
git add database/01_schema.sql database/README.md
```

不建议在不了解修改清单时直接使用 `git add .`。

### 5.4 提交说明

提交类型可以保留常见英文前缀，具体说明使用中文：

```text
feat: 新增停车位查询接口
fix: 修复车辆出场计费错误
docs: 补充数据库初始化说明
refactor: 调整停车记录服务结构
test: 添加计费规则测试
chore: 更新项目基础配置
```

提交示例：

```bash
git commit -m "feat: 新增停车位查询接口"
```

### 5.5 推送并创建 PR

第一次推送当前分支：

```bash
git push -u origin feature/任务名称
```

在 GitHub 创建 Pull Request 时确认：

```text
base: dev  <-  compare: feature/任务名称
```

PR 说明至少包含：

- 本次完成内容。
- 主要修改文件。
- 手动测试方法和结果。
- 是否修改数据库结构或接口格式。
- 尚未解决的问题。

### 5.6 评审和修改

评审者应在 `Files changed` 中检查代码，可使用：

- `Comment`：提出问题或建议。
- `Approve`：确认通过。
- `Request changes`：要求修改后再合并。

收到修改意见后，在原功能分支继续修改：

```bash
git add 具体文件
git commit -m "fix: 根据评审意见修正数据库约束"
git push
```

原 PR 会自动更新，不需要重新创建。

### 5.7 合并后的本地收尾

```bash
git switch dev
git pull origin dev
git branch -d feature/任务名称
git fetch origin --prune
```

如果 `git branch -d` 拒绝删除，不要立即使用 `-D`，先确认 PR 是否真的合并，以及本地是否还有未推送提交。

## 6. 数据库协作约定

### 6.1 每人使用自己的本地数据库

不共享 PostgreSQL 的物理 `data` 目录，也不上传本机生成的数据库文件。团队通过 SQL 脚本同步结构和演示数据。

计划中的统一数据库名：

```text
smart_parking
```

建议将共享配置调整为：

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:15432/smart_parking}
spring.datasource.username=${DB_USERNAME:Niannya}
spring.datasource.password=${DB_PASSWORD}
```

实际密码只放在本机环境变量或未跟踪的本地配置中。

### 6.2 SQL 文件职责

| 文件 | 内容 |
| --- | --- |
| `database/01_schema.sql` | 表、主键、外键、唯一约束、检查约束和索引 |
| `database/02_seed_data.sql` | 演示车辆、停车位、计费规则等测试数据 |
| `database/README.md` | 创建数据库、执行顺序和验证方法 |

SQL 脚本应尽量做到：

- 能在一个新建空数据库中按顺序执行。
- 不包含本机绝对路径。
- 不包含数据库密码。
- 不依赖某位组员已有的手工数据。
- 字段、约束和注释与 ER 图一致。

### 6.3 数据库结构变更流程

1. 从最新 `dev` 创建数据库功能分支。
2. 先更新 ER 图或数据字典。
3. 修改 `01_schema.sql` 或增加迁移脚本。
4. 在新建空数据库中验证脚本。
5. 同步修改实体、Mapper、接口和测试。
6. 在 PR 中明确列出结构变化和执行方法。

不要只在 pgAdmin 或命令行中手工改表而不更新 SQL 文件，否则其他组员无法复现。

## 7. 停车场系统建议数据范围

第一版建议控制为“单停车场、多区域、后台管理端”，先完成完整业务闭环，再增加可选功能。

### 7.1 核心数据表

| 表 | 主要职责 |
| --- | --- |
| `parking_area` | 停车区域，如 A 区、B 区 |
| `parking_space` | 车位编号、类型和当前状态 |
| `vehicle` | 车牌号、车辆类型和车主信息 |
| `parking_record` | 入场时间、出场时间、占用车位和费用 |
| `fee_rule` | 计费单位、免费时长、封顶金额等规则 |
| `payment_order` | 应付金额、实付金额、支付方式和状态 |
| `app_user` | 系统管理员或操作员，可在需要登录时加入 |

表名不建议直接使用 `user`，因为它容易与数据库关键字或系统概念混淆。

### 7.2 第一版业务闭环

1. 管理停车区域和停车位。
2. 登记车辆入场并分配空闲车位。
3. 将车位状态改为占用。
4. 登记车辆出场。
5. 根据规则计算停车费用。
6. 生成支付记录并释放车位。
7. 展示空闲车位数量和当日停车记录。

预约、会员、车牌识别和复杂统计可以作为加分项，不应阻塞第一版闭环。

## 8. 推荐开发顺序

### 阶段一：数据库设计

- 确定业务范围。
- 绘制 ER 图。
- 编写数据字典。
- 创建 `database/01_schema.sql`。
- 创建少量可重复使用的演示数据。

### 阶段二：停车位管理

- 停车区域和停车位查询。
- 新增、修改和停用车位。
- 按区域、类型和状态筛选。

### 阶段三：车辆进出场

- 车辆登记。
- 入场记录和车位占用。
- 出场时间和停车时长。
- 释放停车位。

### 阶段四：计费与支付

- 计费规则维护。
- 后端统一计算费用。
- 支付状态记录。
- 处理重复出场和无入场记录等异常情况。

### 阶段五：统计和验收

- 空闲与占用车位统计。
- 当日入场、出场和收入统计。
- 完整前后端联调。
- 使用全新数据库执行 SQL 并复测。
- 将稳定的 `dev` 通过 PR 合并到 `main`。

## 9. 推荐分工方式

无论如何分工，每位组员都应了解数据库结构和完整业务流程。

一种简单分法：

| 角色 | 主要任务 |
| --- | --- |
| 数据库与后端 | ER 图、建表 SQL、实体、Mapper、Service、接口 |
| 前端 | 页面、表单、表格、接口调用、错误提示 |
| 联调与测试 | 接口测试、边界情况、演示数据、文档与汇报材料 |

不要长期把所有 SQL、所有后端或所有 Git 操作只交给一个人。至少安排一名组员参与 PR 评审和复现测试。

## 10. 不得上传的内容

- 数据库真实密码。
- `.env` 和 `.env.*` 本地环境文件。
- `application-local.properties`。
- `.idea`、个人运行配置和个人绝对路径。
- `frontend/node_modules`。
- `frontend/dist`。
- `backend/target`。
- PostgreSQL 的物理 `data` 目录。
- 临时日志和包含个人信息的导出文件。

提交前检查：

```bash
git status
git diff --cached
git grep -n -i -E "password|passwd|secret|api[_-]?key|access[_-]?token"
```

搜索到 `DB_PASSWORD` 占位符、Maven Wrapper 自带变量或文档说明不等于密码泄露，应检查等号右侧是否为真实值。

## 11. 常见问题

### 11.1 克隆后看不到项目文件

当前远程 `main` 尚未包含项目框架，执行：

```bash
git switch dev
```

### 11.2 `a branch named 'dev' already exists`

说明本地已经有 `dev`，不需要再次创建：

```bash
git switch dev
git pull origin dev
```

### 11.3 `LF will be replaced by CRLF`

这是 Windows 换行符提示，不是提交失败。通常不需要处理。

### 11.4 Git 输出底部显示 `(END)`

Git 正在用分页器显示长输出，按 `q` 返回命令行。

### 11.5 中文文件名显示为数字转义

可以执行：

```bash
git config --global core.quotepath false
```

这只改变显示方式，不会重命名文件。

### 11.6 后端启动失败并提示缺少 `DB_PASSWORD`

在 IDEA 的 `BackendApplication` 运行配置中添加本地环境变量，不要把密码写回 `application.properties`。

### 11.7 前端显示数据加载失败

按顺序检查：

1. 后端是否已在 `8081` 端口启动。
2. `http://localhost:8081/hello` 是否可访问。
3. PostgreSQL 是否启动。
4. 数据库地址、端口、用户名和密码是否正确。
5. 当前数据库是否存在接口查询的表。
6. 浏览器开发者工具中的 Network 和 Console 信息。

### 11.8 推送被拒绝

不要使用强制推送。先确认当前分支，再同步它的远程基线：

```bash
git status
git branch -vv
git fetch origin
```

把错误信息和上述输出交给组员共同判断。
